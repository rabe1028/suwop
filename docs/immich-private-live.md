# Immich private Live Photo read and playback

This candidate reads one explicitly related still/motion pair through the current dedicated PIN session. It does not grant ordinary-list, export/share, editing or multi-resource visibility-write authority. Its merged base is PR #41 (`418fd4d`), including PR #40's metadata observation; no new submitted-head CI or merge is claimed here.

## Discovery and fresh authority

Rust owns the cached `liveDiscovery` projection. A valid observed relation with known unstacked state offers **Live Photoを確認して再生**. A missing relation field, or a valid relation whose stack state is still unknown, projects Unknown and offers **Live Photoの有無を確認**. Explicit null is observed-unlinked and hides the Live action. Malformed/self relations and unsupported RAW/VIDEO, stacked or offline records do not masquerade as playable pairs. Incomplete companion inventory alone does not hide a valid linked parent. Refresh and exact selected observation can replace the hint; the hint itself issues no media request.

Both offered actions still require fresh dedicated-session inspection. Rust fixes the request/plan, scene, grant, generation, parent and motion identities before awaiting. The owned IMAGE parent must currently be locked, explicitly related to its distinct owned VIDEO motion; the motion must explicitly have no forward relation. IDs, checksums, opaque revisions, unstacked state, availability and placement are checked exactly. Motion timeline/archive/hidden/locked placements remain distinct and supported for read. Status/P/M/status and the captured authority epochs are checked around acquisition stages and after native publication. Reverse discovery is informational and never proves a complete mutation closure.

A plan ID, native receipt or cached metadata is not a write grant. C-1 read availability on the tested 3.2.4 and 3.3.3 releases is independent of the exact stable-3.3.3 C-2 write gate. Successful locked access does not promise secrecy through existing album/shared-link or related-resource grants.

## Paired ownership and publication

- Rust issues only the selected P and explicit M original requests. Both byte streams are bounded and hashed against the exact facts; neither an implicit P2 nor unrelated asset becomes a read target. A missing half cannot publish.
- One pair quote, immutable initial budget, shared ledger and acquisition controller account for both originals and named native representations. Known sizes commit upfront; absent sizes use finite incremental bounds. Checked rounding/counter conversion is distinct from the raw receive ceiling. Renewal requires the exact native CAS acknowledgement and fresh pair/session proof; it cannot reset bytes, rename an already completed lease or extend the hard authorization limit.
- Preparation uses the actual matched files and PhotoKit request with a main-actor-owned opaque registry. There is no whole-Live archive Data bridge or Photos-library import. Full materialization and callback/app-owned-work drain are distinct from a loading-cancellation result. Input files and claims remain owned while the prepared object or surface can use them; public APIs do not establish a universal bound on PhotoKit internal copies/I/O.
- Native publication is an atomic hidden-object handoff, not drawing authority. Only the final current Rust Access after the publication receipt and a new pair proof can attach, under exact registered scene/window, current lease and synchronous owner checks. Old acquisition expiry cannot be reused as the published display lifetime.
- Normal Stop/replacement retires only its exact consumer. Key-wide visibility-write barriers join all process-registered consumers touching the selected physical key, including shared-motion and retired/prequote owners, before intent persistence. They do not imply reverse-graph write authority. Unproven cleanup cannot ACK release; failed exact unlink retains ownership for an explicit, proven cleanup attempt.
- Replay is one explicit user command. While native start is pending, it waits for actual willBegin before requesting stop; during playback it stops immediately. Actual didEnd consumes the epoch/consumer/publication-bound command, and a fresh guarded actor turn starts one full playback. Owner/lease invalidation clears pending/queued replay before native stop and object clearing. No automatic replay, EOF-wait workaround or deadline extension is used.
